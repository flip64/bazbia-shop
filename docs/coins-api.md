# API عمومی سکه و پک بازبیا

این نسخه شامل مدل‌های مرحله قبل و API خواندنی روی همان مدل‌هاست.
نیازی به migration جدید نسبت به بسته مدل‌ها ندارد؛ نام migration اولیه همان `coins.0001_initial` است.

## نصب

پوشه `coins` را در ریشه پروژه کپی/جایگزین کنید. در تنظیمات:

```python
INSTALLED_APPS = [
    # ...
    'coins.apps.CoinsConfig',
]
```

در `bazbia_shop/urls.py` در کنار API محصولات اضافه کنید:

```python
path('api/coins/', include('coins.api.urls')),
```

اگر بسته قبلی را نصب کرده‌اید، خط تنظیمات را دوباره اضافه نکنید.
`settings-coins.patch` و `urls-coins.patch` نیز تغییرهای کوچک را نشان می‌دهند؛ اگر قبلاً خطی را افزوده‌اید، patch آن را دوباره اعمال نکنید.
فایل کامل تنظیمات یا URL پروژه در بسته نیست تا تغییرهای جدید خودتان بازنویسی نشود.
DRF از قبل وابستگی پروژه است؛ نیازی به پکیج تازه برای تولید ندارید.

```bash
python manage.py check
python manage.py migrate coins
```

سپس برنامه Django را Restart کنید. این بسته روی سرور اعمال یا روی GitHub push نشده است.

## Endpointها

همه مسیرهای زیر GET، عمومی و فقط خواندنی هستند. POST/PUT/PATCH/DELETE مجاز نیست.
پاسخ JSON و مسیرها دارای اسلش انتهایی هستند.

| مسیر | پاسخ |
|---|---|
| `/api/coins/` | فهرست انواع سکه دارای نمونه متصل به محصول فعال |
| `/api/coins/<slug>/` | شناسنامه نوع سکه، جنس‌ها، مراجع، نوبت‌های ضرب و نمونه‌های فعال |
| `/api/coins/packs/` | فهرست پک‌های دارای حداقل یک نسخه با محتویات ثبت‌شده |
| `/api/coins/packs/<slug>/` | مشخصات پک و نسخه‌های قابل عرضه و محتویات هر نسخه |
| `/api/coins/filters/` | گزینه‌های کشور، دوره، جنس، شکل، سال/تقویم، وضعیت و دیگر فیلترها |

slug سکه همان `CoinType.slug` است؛ slug پک همان `CoinPack.product.slug` است.
شناسه داخل کارت سکه، ID نوع سکه است، نه شناسه محصول یا واریانت.

## فیلترهای دو فهرست

| پارامتر | مقدار |
|---|---|
| `q` | جست‌وجو، حداکثر ۱۲۰ کاراکتر |
| `issuer` | نامک کشور یا قلمرو |
| `period` | نامک دوره |
| `ruler` | نامک حاکم |
| `currency` | نامک واحد پول سکه، نه واحد قیمت فروشگاه |
| `material` | نامک جنس بدنه/مرکز/حلقه/روکش |
| `theme` | نامک موضوع |
| `mint` | نامک ضرابخانه |
| `shape` | کد شکل از پاسخ filters |
| `construction` | مانند `bimetal`، `plated` و `solid` |
| `issue_kind` | `circulation`، `commemorative`، `collector`، `pattern`، `token`، `other` |
| `calendar` | `solar_hijri`، `lunar_hijri`، `gregorian`، `imperial_iran`، `regnal`، `other` |
| `year` | سال دقیق در تقویم انتخابی |
| `year_min`, `year_max` | بازه سال، شامل دو انتها |
| `condition` | مانند `vf`، `xf`، `au` و `unc` |
| `finish` | مانند `standard`، `bu`، `proof`؛ جدا از کیفیت فعلی نمونه |
| `min_price`, `max_price` | قیمت صحیح به تومان، صفر یا بیشتر |
| `in_stock` | `true` فقط موجود؛ `false` فقط نمونه/نسخه ناموجود؛ حذف پارامتر یعنی هر دو |
| `ordering` | `price`، `-price`، `name`، `-name` یا `newest` |
| `page` | از ۱ |
| `page_size` | ۱ تا ۱۰۰، پیش‌فرض ۲۴ |
| `is_complete` | فقط فهرست پک‌ها، `true` یا `false` |

بدون ordering، ابتدا موارد دارای موجودی و سپس قیمت و ID مرتب می‌شوند.
`newest` براساس زمان ایجاد نوع سکه/پک است، نه سال ضرب.
جست‌وجوی سکه روی عنوان کاتالوگی، نام محصول و نوشته رو/پشت است.
جست‌وجوی پک روی نام محصول و توضیحات عمومی پک است.

فیلتر سال بدون calendar خطای ۴۰۰ دارد. year را با year_min/year_max هم‌زمان نفرستید.
پارامتر نامعتبر، گزینه خارج از انتخاب‌ها، بازه معکوس، page_size بالاتر از ۱۰۰ و پارامتر تکراری خطای ۴۰۰ دارند.
هر فیلتر یک مقدار دارد؛ multi-select در این نسخه پیاده نشده است.

تمام فیلترهای مربوط به نمونه سکه باید روی یک نمونه مشترک صدق کنند؛
وجود سکه سال ۱۳۷۳ با کیفیت XF و سکه ۱۳۷۴ با کیفیت VF به معنی وجود سال ۱۳۷۳ با کیفیت VF نیست.
برای فیلتر مشخصات اجزای پک نیز یک جزء در همان نسخه باید هم‌زمان شرایط را داشته باشد.
فیلتر issuer در فهرست پک‌ها روی کشور خود پک نیز اعمال می‌شود؛ پک چندکشوری با issuer خالی در این فیلتر قرار نمی‌گیرد.

نمونه درخواست:

```http
GET /api/coins/?issuer=iran&calendar=solar_hijri&year=1373&construction=bimetal&in_stock=true&ordering=price
GET /api/coins/packs/?calendar=solar_hijri&year=1373&is_complete=false
```

## ساختار پاسخ فهرست

```json
{
  "count": 1,
  "next": null,
  "previous": null,
  "results": [
    {
      "id": 1,
      "name": "۲۵۰ ریالی",
      "slug": "250-rial",
      "issuer": {"id": 1, "name": "ایران", "name_en": "", "slug": "iran"},
      "period": null,
      "denomination_label": "",
      "calendar": "solar_hijri",
      "year_start": null,
      "year_end": null,
      "construction": "bimetal",
      "shape": "round",
      "min_price": "9000",
      "currency": "IRT",
      "in_stock": true,
      "image": null
    }
  ]
}
```

این نمونه ساختار پاسخ است و داده واقعی فروشگاه نیست.
قیمت‌ها رشته عددی به تومان‌اند؛ برای محاسبه در Vue به Number تبدیل شوند.
در کارت، min_price کمترین قیمت نمونه موجودی است که با فیلترها تطبیق دارد؛ اگر هیچ‌کدام موجود نباشند، کمترین قیمت نمونه ناموجود نمایش داده می‌شود.
تصویر کارت هم از همان نمونه‌ای است که قیمت کارت از آن گرفته شده است.
بدون year یا condition کارت ممکن است چند سال/نمونه را نمایندگی کند؛ انتخاب دقیق در جزئیات انجام می‌شود.
موجودی از سرویس فعلی بازبیا می‌آید: انبار داخلی + پیشنهاد معتبر تأمین‌کننده فعال.
این مسیر فقط اطلاعات را می‌خواند و رزرو یا ثبت سفارش انجام نمی‌دهد.

## اتصال صفحه جزئیات به سبد خرید

در جزئیات سکه:

```text
issues[] -> specimens[] -> variant_id
```

در جزئیات پک:

```text
variants[] -> variant_id
variants[] -> items[]
```

هر نمونه/نسخه شامل id، variant_id، product_id، product_slug، sku، price، discount_price،
effective_price، currency، available_stock، can_purchase، sale_mode، condition_notes و images است.
نمونه سکه همچنین حفظ‌شدگی، ایرادها، مشخصات گواهی و اندازه‌گیری واقعی را دارد.
نسخه پک همچنین items، coin_count و packaging_notes را دارد.
coin_count تعداد سکه‌ها در یک پک است؛ available_stock تعداد پک‌های موجود است.

برای افزودن به سبد از endpoint موجود استفاده کنید:

```http
POST /api/orders/cart/add/
Content-Type: application/json
```

```json
{"variant_id": 123, "quantity": 1}
```

عدد ۱۲۳ صرفاً مثال است؛ variant_id را از نمونه/نسخه انتخاب‌شده بردارید، نه id کارت، issue یا specimen.
قیمت را از فرانت ارسال نکنید. can_purchase وقتی موجودی مثبت و effective_price مثبت باشد true است.
این پرچم پیش‌نمایش است؛ موجودی و مجازبودن خرید در مسیر فعلی سبد/سفارش دوباره بررسی می‌شود.
در نمونه اختصاصی، quantity را در فرانت یک نگه دارید؛ محدودیت کامل همه مسیرهای تغییر موجودی از کارهای مرحله بعد است.
این نسخه آزمون خرید کامل/درگاه انجام نمی‌دهد و رفتار سرویس سبد را تغییر نداده است.

## تصاویر

هر تصویر دارای id، url، alt_text، is_main، view_type، pack_item_id و caption است.
view_type یکی از obverse، reverse، edge، detail، pack یا certificate است؛ تصاویر بدون برچسب null دارند.
برای عکس جزء مشخص در پک، pack_item_id با id ردیف items تطبیق دارد.
فایل محلی به URL مطلق تبدیل می‌شود؛ source_url تصاویر خارجی نیز پشتیبانی می‌شود.
در این مرحله فایل تصویر دوباره ذخیره یا وارد نمی‌شود.

## نمایش و حریم اطلاعات

- محصول غیرفعال و نمونه‌های متصل به آن نمایش داده نمی‌شوند.
- نمونه ناموجود متصل به محصول فعال همچنان قابل مشاهده است؛ can_purchase برابر false است.
- نوع سکه بدون هیچ نمونه متصل به محصول فعال، ۴۰۴ دارد؛ این API کاتالوگ عمومی مستقل نیست.
- پک یا نسخه بدون اجزا در فهرست/جزئیات عمومی ظاهر نمی‌شود.
- دوره، حاکم و واحد پول به صورت خلاصه شناسنامه‌ای هستند؛ جزئیات فیزیکی و جنس در پاسخ سکه آمده است.
- اطلاعات محل نگهداری، قیمت خرید، درصد سود و یادداشت‌های داخلی مدل‌های مرجع در خروجی نیست.
- شرح اصالت، کیفیت و ایرادها در خروجی عمومی‌اند؛ در این فیلدها یادداشت خصوصی ننویسید.
- filters گزینه‌های متصل به انواع سکه با نمونه فعال یا جزء پک فعال را می‌دهد؛ فیلترهای آبشاری وابسته به درخواست نیستند.
- تغییر اطلاعات تاریخی سفارش‌ها، انتقال موجودی، مدیریت انتشار اختصاصی و API مدیریتی در این مرحله انجام نشده‌اند.

## بررسی و آزمون

```bash
python manage.py test coins --settings=coins.test_settings
python manage.py check --settings=coins.test_settings
python manage.py makemigrations coins --check --dry-run --settings=coins.test_settings
```

۵۵ آزمون مدل و API روی SQLite مجزا پاس شدند؛ از جمله هم‌زمانی فیلترها روی یک نمونه،
پنهان‌بودن محصولات غیرفعال، حذف اطلاعات خصوصی، موجودی تأمین‌کننده، قیمت تخفیفی،
مسیریابی، رد درخواست نوشتن، صفحه‌بندی و تعداد ثابت queryهای فهرست.
فهرست سکه با نتیجه در آزمون ۳ query دارد: شمارش، صفحه و تصاویر؛ موجودی در زیرپرس‌وجوی SQL محاسبه می‌شود.
آزمون روی MySQL واقعی سرور و تنظیمات کامل تولید انجام نشده است.
