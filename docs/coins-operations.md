# تکمیل بک‌اند فروش سکه و پک آماده بازبیا

این بسته مدل‌ها، API مرحله قبلی و کنترل‌های عملیاتی جدید را شامل می‌شود.
مبنای فایل‌های مشترک: bazbia-shop commit `4d512ea022012953953110bef5538990a93a5870`.
هیچ تغییری روی سرور یا GitHub اعمال نشده است.

## نصب و ارتقا

۱. از دیتابیس و فایل‌های فعلی نسخه پشتیبان بگیرید.
۲. پوشه coins را کپی/به‌روزرسانی کنید. فایل‌های مشترک داخل بسته را با نسخه خودتان مقایسه کنید؛
اگر بعد از commit مبنا تغییر کرده‌اند، از `integration.patch` برای ادغام تغییرات استفاده کنید و کل فایل را بی‌بررسی جایگزین نکنید.
`CHANGELOG-files.txt` فهرست دقیق فایل‌ها را دارد. فایل تنظیمات کامل و URL کامل پروژه در بسته نیست.
۳. اگر قبلاً اضافه نکرده‌اید، در INSTALLED_APPS خط زیر را اضافه کنید:

```python
'coins.apps.CoinsConfig',
```

در URLهای پروژه:

```python
path('api/coins/', include('coins.api.urls')),
```

۴. در محیط مجازی واقعی سرور:

```bash
python manage.py check
python manage.py migrate --plan
python manage.py migrate
python manage.py audit_coins
```

migrationهای تازه:
- `coins.0002_coinpackvariant_is_published_and_more`
- `orders.0008_orderitem_catalog_snapshot`
- `payments.0002_payment_requires_review`

migration اولیه coins موجود حفظ شده است؛ migrationهای اجراشده را حذف یا دوباره تولید نکنید.
هنگام اعمال migration و جایگزینی فایل‌ها، ورود سفارش جدید را موقتاً متوقف و پس از پایان برنامه را Restart کنید.
وابستگی جدید برای تولید اضافه نشده؛ Django 5.2 و DRF و requests از وابستگی‌های پروژه‌اند.

## تفاوت‌های این نسخه

### نمونه اختصاصی و نمونه مشابه

sale_mode=unique یعنی یک جسم مشخص با عکس واقعی؛ stock فقط صفر یا یک است.
sale_mode=similar یعنی چند سکه/پک همسان؛ موجودی تعدادی مانند ۱۰ یا ۲۰ مجاز است.

کنترل در save و QuerySet.update و bulk_update اعمال شده؛ عبارت F نیز پس از محاسبه بررسی و در صورت خطا rollback می‌شود.
برای unique، موجودی + تعداد موجود در سفارش‌های pending/paid/shipped/completed + مصرف در پک نباید بیشتر از یک شود.
بنابراین در زمان رزرو یا پس از فروش نمی‌توان همان شناسه را با افزایش دستی stock دوباره فروخت.
لغو سفارش در یک تراکنش، رزرو را آزاد و موجودی/لات را بازمی‌گرداند؛ لغو مجدد موجودی را افزایش نمی‌دهد.
بازکردن پک و مرجوعی برای فروش مجدد یک نمونه اختصاصی نیازمند سرویس جداست و این نسخه آن را خودکار انجام نمی‌دهد.

نمونه اختصاصی و پک آماده فقط از موجودی داخلی تأمین می‌شوند؛ پیشنهاد مثبت و فعال تأمین‌کننده برایشان رد می‌شود.
سکه‌های مشابه همچنان می‌توانند از تأمین‌کنندگان معتبر قبلی عرضه شوند.
تغییر صرف قیمت با update_fields محدود، قفل موجودی اضافی ایجاد نمی‌کند.

### انتشار صریح

CoinSpecimen و CoinPackVariant فیلد is_published دارند؛ پیش‌فرض False است.
مهاجرت، داده‌های قبلی سکه را خودکار منتشر نمی‌کند؛ پس از ثبت تصاویر و بررسی هر نمونه آن را منتشر کنید.

شرایط انتشار سکه:
- قیمت نهایی مثبت؛
- تصاویر قابل استفاده و برچسب‌خورده obverse و reverse روی همان واریانت.

شرایط انتشار نسخه پک:
- قیمت مثبت و حداقل یک جزء؛
- سازگاری سال، تقویم و کشور؛
- عکس کامل با view_type=pack؛
- عکس رو و پشت هر جزء، با pack_item_id مربوط به همان نسخه.

این عکس‌ها را از ProductVariantImage و CoinImageDetail ثبت کنید؛ نام فایل یا عکس عمومی محصول کافی نیست.
محصول اصلی نیز باید is_active=True باشد. انتشار نمونه ناموجود مجاز است، خرید آن مجاز نیست.
اگر بعداً تصویر لازم حذف یا قیمت صفر شود، API اختصاصی آن نمونه را پنهان می‌کند و مسیر خرید نیز آن را رد می‌کند.
همه مسیرهای سبد و ثبت سفارش مجدداً شرایط را بررسی می‌کنند؛ اتکا به وضعیت نمایش فرانت کافی نیست.
ورود به سبد و سفارش برای سکه، تطبیق stock داخلی با لات‌های خرید را نیز بررسی می‌کند.

### endpoint مدیریتی انتشار

```http
POST /api/coins/manage/coin/12/publish/
POST /api/coins/manage/pack/5/publish/
```

```json
{"is_published": true}
```

شناسه coin، ID مدل CoinSpecimen و شناسه pack، ID مدل CoinPackVariant است؛ نه ProductVariant.
برای خارج‌کردن از انتشار false ارسال کنید. این مسیرها IsAdminUser دارند و فقط کاربر staff با احراز هویت پذیرفته می‌شود.
همچنین فیلد انتشار در ادمین Django قابل ویرایش است؛ خطاهای شرایط انتشار نمایش داده می‌شوند.

### آماده‌سازی پک از موجودی تکی

```http
POST /api/coins/manage/assemble/
Content-Type: application/json
Authorization: Bearer <staff-token>
```

```json
{
  "pack_variant_id": 5,
  "quantity": 2,
  "request_key": "pack-batch-1373-001",
  "sources": [
    {"item_id": 8, "variant_id": 41, "quantity": 4},
    {"item_id": 9, "variant_id": 42, "quantity": 2}
  ]
}
```

اعداد صرفاً نمونه‌اند. در این مثال، هر پک ۲ عدد از جزء ۸ و ۱ عدد از جزء ۹ دارد؛
پس برای ساخت ۲ پک، مجموعاً ۴ و ۲ سکه مصرف می‌شوند.
quantity هر source، مجموع مصرف برای تمام پک‌های این عملیات است، نه تعداد در یک پک.
یک جزء می‌تواند از چند واریانت منبع مناسب تأمین شود؛ جمع مصرف باید دقیقاً با تعریف آن جزء تطبیق کند.

- فقط سکه داخلی متصل به CoinSpecimen و نوبت ضرب همان جزء قابل مصرف است.
- اگر حفظ‌شدگی جزء مشخص شده باشد، منبع باید همان درجه را داشته باشد.
- منبع و مقصد نباید یک واریانت باشند.
- stock و جمع quantity_remaining لات‌های داخلی منبع باید تطبیق داشته باشند.
- ردیف‌های واریانت با ترتیب ثابت قفل و لات‌ها با FIFO مصرف می‌شوند.
- موجودی سکه‌های تکی کاهش و موجودی پک آماده افزایش می‌یابد.
- بهای خرید مصرف‌شده به InventoryLotهای جدید پک منتقل می‌شود.
- در صورت تقسیم‌ناپذیری هزینه بر تعداد پک‌ها، دو لات ساخته می‌شود تا جمع هزینه حتی یک تومان جابه‌جا نشود.
- PackAssembly و PackAssemblyAllocation و InventoryMovement سابقه عملیات را ثبت می‌کنند.
- request_key برای تکرار همان درخواست، نتیجه قبلی را برمی‌گرداند؛ ورودی متفاوت با همان کلید رد می‌شود.
- کمبود موجودی یا خطای هر جزء، کل انتقال را rollback می‌کند.
- پس از آماده‌سازی، ترکیب و کیفیت اجزای همان نسخه تغییر نمی‌کند؛ برای ترکیب متفاوت نسخه جدید بسازید.

این endpoint انتقال موجودی را ثبت می‌کند؛ بسته‌بندی فیزیکی و تطبیق عکس‌ها با محتوای واقعی مسئولیت مدیر است.
برای موجودی آماده‌ای که پیش‌تر خارج از سیستم خریده‌اید، ثبت ورود خرید/لات پک از مسیر فعلی purchases امکان‌پذیر است.
برای آن موجودی دوباره assemble اجرا نکنید. تغییر عدد stock به‌تنهایی ورود خرید محسوب نمی‌شود.

### سابقه ثابت سفارش

OrderItem.catalog_snapshot یک JSON نسخه‌دار از اطلاعات عمومی خرید را در لحظه ثبت سفارش نگه می‌دارد.
برای سکه: عنوان، شناسنامه، نوبت ضرب، نمونه انتخابی، کیفیت، گواهی و تصاویر.
برای پک: عنوان، سال و تقویم، تعریف کامل‌بودن، نسخه، فهرست اجزا و کیفیت آن‌ها.

فیلد در API سفارش خروجی داده می‌شود و قابل ویرایش از API نیست.
تغییر شناسنامه یا توضیحات فعلی، مشخصات سفارش قدیمی را تغییر نمی‌دهد.
نام نمایش‌داده‌شده OrderItem برای خریدهای جدید نیز از snapshot می‌آید.
به سفارش‌های قدیمی snapshot تخمینی اضافه نمی‌شود؛ مقدار آن‌ها {} می‌ماند.
این snapshot آدرس تصاویر را نگه می‌دارد، نه یک کپی مستقل از بایت‌های تصویر؛ حذف فیزیکی فایل می‌تواند تصویر قدیمی را از دسترس خارج کند.
برای OrderItem سکه/پک از create/save استفاده کنید؛ bulk_create آن‌ها برای جلوگیری از دورزدن snapshot رد می‌شود.
بازنویسی گروهی snapshot یا تغییر واریانت یک ردیف دارای snapshot نیز رد می‌شود.

### پرداخت و لغو

برای سفارش دارای سکه یا پک، تا زمانی که Payment در وضعیت processing است، لغو سفارش رد می‌شود؛ ابتدا نتیجه پرداخت باید مشخص شود.
اگر پرداختی پس از لغو تأیید شود، تراکنش موفق ثبت می‌شود اما سفارش لغوشده دوباره paid نمی‌شود و موجودی آزادشده مصرف نمی‌شود.
requires_review=True و شرح مناسب ثبت می‌شود؛ در ادمین «پرداخت‌ها» می‌توان این موارد را فیلتر کرد.
این وضعیت به معنای تحویل کالا یا استرداد خودکار وجه نیست؛ مدیر باید با درگاه تطبیق و استرداد وجه را انجام دهد.
requires_review در پاسخ API پرداخت نیز وجود دارد تا فرانت پیام درست نمایش دهد.

سرویس mock فقط payment.gateway=mock را در محیط PAYMENT_GATEWAY=mock تأیید می‌کند؛
از آن برای تأیید پرداخت واقعی نمی‌توان استفاده کرد. زرین‌پال همچنان باید از callback و Verify واقعی تأیید شود.
قفل سفارش در تأیید پرداخت با مسیر ایجاد پرداخت هم‌ترتیب شده است.

## بررسی قبل از فعال‌کردن فروش

```bash
python manage.py audit_coins
```

دستور فقط خواندنی است: محدودیت موجودی، ناسازگاری لات‌ها، شرایط انتشار و روابط را بررسی می‌کند.
برای نمونه‌های قدیمی بدون لات، ابتدا بهای خرید و ورود واقعی را با ابزار خرید/انبار ثبت کنید؛
ساخت خودکار لات با بهای خرید حدسی انجام نشده است.

## اعتبارسنجی انجام‌شده و محدوده عملی

۱۰۰ آزمون روی Django 5.2.18 و Python 3.12 و SQLite مجزا پاس شده است:
- خرید واقعی از endpoint فعلی سبد و CreateOrder و لغو؛
- خرید و لغو پک، بدون مصرف دوباره موجودی تکی؛
- نگهداری بهای خرید، FIFO و گردکردن دقیق؛
- تکرار درخواست، rollback، کنترل unique و مشابه؛
- انتشار و عکس، اطلاعات عمومی و فیلترها؛
- snapshot ثابت و جلوگیری از دورزدن گروهی؛
- ایجاد درخواست پرداخت آزمایشی، تأیید تکراری، لغو در processing و پرداخت دیرهنگام؛
- رد تأیید mock برای تراکنش درگاه واقعی.

```bash
python manage.py test coins --settings=coins.test_settings
python manage.py makemigrations coins orders payments products suppliers --check --dry-run --settings=coins.test_settings
```

SQLite رفتار قفل ردیفی MySQL را شبیه‌سازی نمی‌کند. محیط این جلسه MySQL و اعتبارنامه درگاه واقعی نداشت؛
بنابراین آزمون هم‌زمانی روی MySQL سرور، callback واقعی زرین‌پال و پیامک/حسابداری تولید انجام نشده است.
قبل از پذیرش سفارش واقعی، نصب و check و audit را در محیط واقعی اجرا و یک خرید و لغو کنترل‌شده بررسی کنید.
کوئری SQL خام، _raw_delete، _update خصوصی Django و دستکاری مستقیم دیتابیس خارج از guardهای برنامه‌اند؛
از API، سرویس‌ها و managerهای عمومی استفاده کنید.

این مرحله صفحه Vue و داشبورد سفارشی، بازکردن پک، استرداد وجه خودکار و زمان‌بندی انقضای سفارش پرداخت‌نشده را اضافه نمی‌کند.
این موارد مانع شروع پیاده‌سازی فرانت نیستند؛ سفارش پرداخت‌نشده فعلاً تا لغو مدیر/مشتری موجودی را نگه می‌دارد.
